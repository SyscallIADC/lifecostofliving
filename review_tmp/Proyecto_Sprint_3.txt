1. Objetivo
Este sprint representa la culminación del proyecto y plantea la creación de una arquitectura
Lambda o Kappa , en la que una unidad de negocio consume datos en tiempo real desde el
broker y, cuando sea necesario, consulta eventos históricos desde el event store .
Se asume el trabajo de los sprints anteriores: los feeders publican eventos en ActiveMQ y el
módulo Event Store Builder (Sprint 2) los persiste en el event store . En este Sprint 3 se añade
un módulo nuevo ( business-unit ) que construye y mantiene un datamart para responder a
consultas del usuario nal.
Se desarrollará un nuevo módulo llamado business-unit , cuyo propósito es explotar los datos
en tiempo real o en diferido para generar valor para un usuario nal, a través de análisis,
consultas o recomendaciones. Esta funcionalidad debe ser accesible mediante una interfaz de
usuario, ya sea en forma de API REST, interfaz gráca (GUI) o línea de comandos (CLI). La

2.1. Requisitos operacionales
1. El sistema debe funcionar en local. La interfaz del usuario nal debe ser una API REST,

2. El módulo business-unit estará desarrollado en Java 21, al igual que el resto del pro-

3. El entorno de desarrollo debe seguir siendo IntelliJ.
4. El repositorio del proyecto debe reejar progreso mediante al menos 5 commits adicionales

2.2. Requisitos funcionales
1. Consumo en tiempo real
business-unit debe estar suscrito a los topics necesarios del broker ActiveMQ y
consumir los eventos a medida que se producen.
Se debe gestionar la continuidad del consumo (reconexiones y recuperación). Se
recomienda usar una suscripción durable cuando aplique.
A partir de estos eventos, debe alimentar un datamart local y mantenerlo actualizado
en todo momento.
2. Acceso a eventos históricos
Si se requieren datos pasados, el módulo business-unit puede acceder directamente
al event store para leer los cheros .events almacenados (un evento por línea en
formato JSON Lines/NDJSON).
Debe implementar un sistema para cargar estos eventos históricos y tratarlos de for-
ma similar a los eventos en tiempo real (por ejemplo, para inicializar/reconstruir
el datamart al arrancar).
3. Generación de valor para un usuario nal
La unidad de negocio debe implementar una o más funcionalidades que respondan
a una necesidad o caso de uso concreto: predicciones, análisis comparativos, alertas,
recomendaciones, etc.
